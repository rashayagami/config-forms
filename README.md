# form-config

Forms for React and Next.js described by a small JSON configuration. The library supplies the
components, styling and behaviour; a configuration only says which registered components to use,
their props, where they go, how they depend on each other, which registered actions run on which
events, and how the form is split into pages. A configuration never contains code, HTML or CSS, so
it can be written by people or generated by a model and checked before anything renders.

- **@form-config/core**: framework-free. Config types, the component catalog, the compiler
  (validation + normalization with structured errors), conditions and dependency effects, value
  validation, navigation and submission logic, JSON themes, responsive layout CSS, and helpers for
  AI generation. Safe to import on a server.
- **@form-config/react**: renders a compiled config with [Base UI](https://base-ui.com) controls,
  with all form state in [react-hook-form](https://react-hook-form.com).

Values live only in the form's in-memory state while it is mounted. Nothing is persisted and
nothing is sent over the network: submissions go to handlers your application registers.

## Quick start

```bash
pnpm add @form-config/core @form-config/react react react-dom
```

```tsx
import { SchemaForm } from '@form-config/react';
import '@form-config/react/styles.css';

const config = {
  version: 1,
  id: 'signup',
  components: [
    { id: 'name', type: 'text', label: 'Name', required: true },
    { id: 'email', type: 'text', label: 'Email', inputType: 'email', required: true },
    {
      id: 'plan',
      type: 'radio',
      label: 'Plan',
      options: [
        { label: 'Free', value: 'free' },
        { label: 'Team', value: 'team' },
      ],
    },
    { id: 'seats', type: 'number', label: 'Seats', min: 2 },
  ],
  layout: [{ type: 'row', children: ['name', 'email'] }, 'plan', 'seats'],
  dependencies: [
    { when: { field: 'plan', op: 'eq', value: 'team' }, effect: 'show', target: 'seats' },
    { when: { field: 'plan', op: 'eq', value: 'team' }, effect: 'require', target: 'seats' },
  ],
};

export function Signup() {
  return <SchemaForm config={config} onSubmit={(values) => console.log(values)} />;
}
```

`onSubmit` receives validated values keyed by component id:
`{ name: 'Ada', email: 'ada@example.com', plan: 'team', seats: 5 }`. Hidden fields are left out.

`SchemaForm` throws a `ConfigError` for an invalid configuration, and an `Error` when the config
names a validator, submit handler or action you did not supply. To check a config without
rendering, call `compileConfig(config)` from `@form-config/core`.

## Next.js

The package works with the App Router and the Pages Router.

- Import `@form-config/react/styles.css` once, in the root layout.
- `SchemaForm`, `ThemeProvider` and every built-in field are client components; their modules
  carry `"use client"`, so you can render them from a server component without wrapping them.
  Callbacks (`onSubmit`, `handlers`, `validators`) are functions, so the component that passes
  them must itself be a client component.
- `SchemaResponse` (the read-only view) has no hooks and renders in server components.
- Nothing touches `window` or `document` at import time, and the markup is deterministic, so
  server rendering and hydration produce the same output.
- `compileConfig`, `describeCatalog` and the theme functions run in route handlers and server
  actions, for example to validate a generated config before storing it.

## The configuration format

A configuration is one JSON object, version 1:

| Key                                                | Required    | Meaning                                                                                 |
| -------------------------------------------------- | ----------- | --------------------------------------------------------------------------------------- |
| `version`                                          | yes         | Always `1`. Other versions are rejected.                                                |
| `id`                                               | yes         | An identifier for the form.                                                             |
| `components`                                       | yes         | Every component instance: `{ "id", "type", ...props }`.                                 |
| `layout` or `pages`                                | one of them | Where components appear: one layout, or pages each with a layout.                       |
| `dependencies`                                     | no          | Declarative rules: when a condition holds, apply an effect to a target.                 |
| `navigation`                                       | no          | Pages only: `progress` (`steps`, `bar`, `none`), `allowBack`, `validateOnNext`, labels. |
| `submission`                                       | no          | `strategy` (`final` or `perStep`) and the handler names.                                |
| `initialValues`                                    | no          | Values by component id; override each component's `defaultValue`.                       |
| `validateOn`                                       | no          | `submit` (default), `blur` or `change`. Fields revalidate on change after a submit.     |
| `hiddenValues`                                     | no          | `omit` (default) leaves hidden fields out of submissions; `keep` includes them.         |
| `submitLabel`, `showReset`, `title`, `description` | no          | Labels and headings.                                                                    |
| `theme`                                            | no          | The name of a theme registered with a `ThemeProvider`.                                  |

Rules that keep generated configs unambiguous:

- **Ids** are identifiers (`[A-Za-z][A-Za-z0-9_]*`), unique across components, layout nodes and
  pages. For a form control, the id is also the value key.
- **One representation per concept.** Constraints are props (`required`, `minLength`, `pattern`,
  `matches`, ...); conditional behaviour is a dependency; behaviour on events is an action.
- **Nothing is dropped or guessed.** Unknown properties, unknown types, bad references, a component
  placed twice or never placed, and contradictions are all errors.
- **Defaults are filled in by the compiler**, so a config states only what differs.

`compileConfig` turns this compact form into a `NormalizedConfig`: every catalog default applied,
every layout node resolved per breakpoint, every page's fields listed, every dependency with its
targets and sources. The same input and compiler version always produce the same output, and
results are cached per input object (`compileConfig(sameObject)` costs nothing the second time).

### Errors

Every issue carries a code, a JSON Pointer, the part it belongs to, and usually what was expected
and a likely fix:

```json
{
  "severity": "error",
  "code": "unknown_component_type",
  "path": "/components/1/type",
  "target": { "kind": "component", "id": "score", "index": 1 },
  "componentId": "score",
  "message": "Unknown component type \"slider\"",
  "expected": "\"text\", \"textarea\", \"number\", ...",
  "suggestion": "Use a type from the catalog."
}
```

Suggestions cover typos (`requird` → `required`) and the words a model tends to use instead of the
canonical ones (`equals` → `eq`, `reveal` → `show`, `stack` → `column`, `phone` → `mobile`).

Codes: `invalid_json`, `invalid_type`, `missing_property`, `unknown_property`,
`unsupported_version`, `invalid_id`, `duplicate_id`, `unknown_component_type`, `invalid_prop`,
`invalid_value`, `unknown_reference`, `invalid_layout`, `invalid_nesting`, `invalid_context`,
`duplicate_placement`, `unplaced_component`, `invalid_condition`, `unsupported_effect`,
`ambiguous_row_reference`, `self_dependency`, `dependency_cycle`, `conflicting_effects` (a
warning), `unknown_event`, `unknown_action`, `invalid_action_args`, `invalid_action_context`,
`incompatible_submission`, `unknown_handler`, `unused_handler`, `limit_exceeded`.

An unknown `type` is an invalid config. There is no "unknown component" at render time: the
compiler checks types against the registry's own catalog, so a config that compiles can always be
rendered by the registry it was compiled for.

## Components and the catalog

| Type                                       | Value                    | Notes                                                                                                   |
| ------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `text`                                     | string (`''` empty)      | `inputType`, `placeholder`, `autoComplete`, `minLength`, `maxLength`, `pattern`, `matches`              |
| `textarea`                                 | string                   | `rows`, `minLength`, `maxLength`                                                                        |
| `number`                                   | number or `null`         | `min`, `max`, `step`; never a string, never `NaN`                                                       |
| `date`                                     | `"YYYY-MM-DD"` or `null` | `min`, `max`                                                                                            |
| `select`                                   | option value or `null`   | `options`, `placeholder`                                                                                |
| `combobox`                                 | option value or `null`   | type to filter; `emptyText`                                                                             |
| `multiselect`                              | array of option values   | `minItems`, `maxItems`                                                                                  |
| `radio`                                    | option value or `null`   | `orientation`                                                                                           |
| `checkbox-group`                           | array of strings         | `orientation`, `minItems`, `maxItems`                                                                   |
| `checkbox`                                 | boolean                  | `required` means it must be checked                                                                     |
| `switch`                                   | boolean                  |                                                                                                         |
| `repeater`                                 | array of row objects     | `item` (a layout of components placed only in the row), `minItems`, `maxItems`, `addLabel`, `itemLabel` |
| `heading`, `paragraph`, `alert`, `divider` | none                     | display only                                                                                            |
| `button`                                   | none                     | raises `click` for an action                                                                            |

Every field also takes `label` (required), `description`, `required`, `disabled`, `readOnly`,
`defaultValue`, `validator` and `messages`.

The full machine-readable catalog (`defaultCatalog`, `ComponentSpec`) records for each type its
props with types, allowed values and defaults; its value semantics; its events; the dependency
effects it supports; its accessibility behaviour; whether it holds children; and where it may be
placed (`form`, `repeater`).

## Layout and responsive behaviour

A layout is an array of component ids and layout nodes:

```json
[
  {
    "type": "section",
    "title": "Contact",
    "children": [{ "type": "row", "children": ["name", "email"] }]
  },
  {
    "type": "grid",
    "columns": 3,
    "children": ["city", "region", { "type": "column", "span": 2, "children": ["notes"] }]
  },
  "terms"
]
```

| Node      | Purpose                            | Props                                                          |
| --------- | ---------------------------------- | -------------------------------------------------------------- |
| `column`  | stack vertically                   | `gap`, `maxWidth`, `span`, `visibleOn`                         |
| `row`     | side by side, stacking when narrow | `gap`, `stackBelow`, `align`, `justify`, `span`, `visibleOn`   |
| `grid`    | equal columns                      | `columns`, `gap`, `span`, `visibleOn`                          |
| `section` | titled region (top level only)     | `title`, `description`, `gap`, `maxWidth`, `visibleOn`         |
| `group`   | related fields under a legend      | `title`, `description`, `gap`, `maxWidth`, `span`, `visibleOn` |

Nesting is restricted: sections only at the top level, groups not inside groups, rows and grids
contain components, columns and groups. Each component is placed exactly once.

Responsive values are a single value or `{ "mobile", "tablet", "desktop" }`, resolved mobile
first (a missing breakpoint inherits from the one below). `"columns": 3` means one column on
mobile, two on tablet and three on desktop.

Breakpoints are widths of the form's own container, implemented with CSS container queries, so a
form in a 300px sidebar lays out like a phone while one in the main column of the same page lays
out like a desktop. Defaults: tablet from 640px, desktop from 1024px. Change them per provider or
per form, without touching any config:

```tsx
<ThemeProvider breakpoints={{ tablet: 560, desktop: 960 }}>...</ThemeProvider>
```

No JavaScript measures anything: changing size never re-renders the form or touches its state.
`visibleOn` is for presentational content only; the compiler rejects it around form fields,
because a field hidden on one screen size could never be filled in there.

## Dependencies

```json
{
  "when": { "field": "housing", "op": "eq", "value": "rent" },
  "effect": "show",
  "target": "landlord"
}
```

- **Conditions**: `{ field, op, value }` with `eq`, `neq`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte`
  (numbers and dates), `includes` (multi-choice fields), `filled`, `empty`; and
  `{ "all": [...] }`, `{ "any": [...] }`, `{ "not": {...} }`. They are evaluated by a closed
  interpreter; nothing is executed.
- **State effects** hold while the condition holds: `show`, `hide`, `enable`, `disable`,
  `require`, `optional`, `options` (replace the target's options).
- **Value effects** run once each time the condition becomes true after a change: `clear`, `set`
  (with `value`). Conditions that already hold on load or reset do not fire.
- **Targets** are components, layout nodes with an `id`, or pages (pages and layout nodes take
  `show`/`hide` only). One rule may list several targets.
- **Precedence** is fixed: hide beats show, disable beats enable, optional beats require, the first
  matching `options` rule wins, and later `set` writes win. Contradictory rules compile with a
  `conflicting_effects` warning.
- **Repeaters**: a condition on a field of a repeater's item applies per row and may only target
  fields of the same item.
- **Rejected**: references to missing ids, effects a target does not support, a component hiding
  itself or the container of its own source, and cycles of value effects.

Hidden values are never cleared implicitly. They stay in the form's state (so showing the field
again restores what was typed), are not validated, and are left out of submissions unless
`hiddenValues` is `keep`. Use a `clear` effect to empty a field on purpose. Disabled and read-only
fields are not validated; their values are submitted.

## Actions

Components raise events; a config names the registered action to run:

```json
{
  "id": "edit",
  "type": "button",
  "label": "Edit travellers",
  "on": { "click": { "action": "navigation.go_to_page", "args": { "page": "people" } } }
}
```

| Action                                   | Args             | Where                                                           |
| ---------------------------------------- | ---------------- | --------------------------------------------------------------- |
| `form.validate`                          |                  | any form                                                        |
| `form.validate_and_submit`               |                  | any form; runs the current page's submission under the strategy |
| `form.reset`                             |                  | any form                                                        |
| `navigation.next`, `navigation.previous` |                  | multi-page forms                                                |
| `navigation.go_to_page`                  | `page` (page id) | multi-page forms; forward jumps validate the pages passed       |

The compiler checks the event, the action, its arguments and its context. The form already
renders Submit, Next and Previous, so buttons are only needed for extra actions.

## Pages and submission

```json
{
  "pages": [
    {
      "id": "applicant",
      "title": "About you",
      "layout": ["name", "phone"],
      "submission": { "handler": "shelter.saveApplicant" }
    },
    { "id": "home", "title": "Your home", "layout": ["housing", "garden"] },
    {
      "id": "review",
      "title": "Review",
      "layout": ["consent"],
      "submission": { "handler": "shelter.submit", "payload": "all" }
    }
  ],
  "submission": { "strategy": "perStep" }
}
```

- Next validates the current page (unless `validateOnNext` is false); Previous never validates.
- Pages can be hidden by dependencies; navigation, progress and validation skip hidden pages.
- Answers on every page stay in memory while the form is mounted, whichever page is shown.

`submission.strategy` decides how values reach the application:

- **`final`** (default): pages only validate. On the last visible page, Submit validates the whole
  form (going to the first page with an error if needed) and calls the form's handler, or the
  `onSubmit` prop when the config names none. Page `submission` entries are rejected.
- **`perStep`**: a page with a `submission` shows a submit button instead of a bare Next. Submitting
  validates that page and calls its handler with the page's values (`payload: "page"`, the default)
  or every value so far (`"all"`). On success it moves on (`advanceOnSuccess`, default true). Next
  will not pass a page that has a handler until it is submitted, and asks for a resubmission when
  that page's values changed since (`requireStepSubmission`, default true). The last page's handler
  is the final submission and validates the whole form; if the last page has no handler, the
  form-level `handler` (or `onSubmit`) is used. Naming both for an always-present last page is an
  `unused_handler` error.

Handlers are application code:

```tsx
<SchemaForm
  config={config}
  handlers={{
    'shelter.saveApplicant': async (values, { pageId }) => api.save(pageId, values),
    'shelter.submit': async (values) => api.submit(values),
  }}
  onSubmissionChange={(state) => console.log(state.status)}
/>
```

Submission state is `idle`, `submitting`, `succeeded` or `failed`. While submitting, the button
shows a spinner in place (its size does not change) and further submits are ignored. A handler
that throws marks the submission failed, shows the error's message on the form, and keeps the user
on the page with every value intact.

## Validation

Constraints run in a fixed order and each field shows its first failure: required, the value's own
type (a number, a date, one of the current options), then length, item count, range, `pattern`
(matched against the whole value), `matches` (equal to another field) and `validator`.

```tsx
<SchemaForm
  config={config}
  validators={{
    postcode: (value) => (/^\d{5}$/.test(String(value)) ? undefined : 'Enter five digits.'),
  }}
  messages={{ required: 'Please fill this in.' }}
/>
```

A component's `messages` prop overrides the defaults for that field. Validation on change checks
only the changed field; a whole page or form is checked on Next and Submit.

## Themes

Themes are JSON, separate from form configs:

```json
{
  "theme": {
    "name": "my-company",
    "colors": {
      "primary": "#7C3AED",
      "primaryForeground": "#FFFFFF",
      "background": "#FFFFFF",
      "foreground": "#18181B"
    },
    "dark": {
      "colors": { "primary": "#A78BFA", "background": "#0F0F12", "foreground": "#F4F4F5" }
    },
    "radius": { "small": "4px", "medium": "8px", "large": "12px" }
  }
}
```

```tsx
<ThemeProvider theme={companyTheme} themes={[campaignTheme]} colorScheme="system">
  <SchemaForm config={config} onSubmit={save} />
  <SchemaForm config={{ ...config, theme: 'campaign' }} onSubmit={save} />
  <SchemaForm config={config} theme={otherTheme} colorScheme="dark" onSubmit={save} />
</ThemeProvider>
```

- **Tokens**: `primary`, `primaryForeground`, `secondary`, `secondaryForeground`, `background`,
  `foreground`, `surface`, `surfaceForeground`, `muted`, `mutedForeground`, `border`, `input`,
  `ring`, `success`, `warning`, `danger`, `info`; radii `small`, `medium`, `large`.
- **Required**: `primary`, `primaryForeground`, `background`, `foreground` (and `background`,
  `foreground` in `dark`). The rest fall back: surfaces and borders derive from the background and
  foreground, `ring` from `primary`, status colours from tuned defaults. In dark mode, unspecified
  tokens derive from the dark base colours, not from light overrides.
- **Validation**: colours must be hex or plain `rgb()`/`hsl()`/`oklch()`-style values and radii
  `px`, `rem` or `em`; anything else (including `url()` or `;`) is an error, so a theme cannot
  inject CSS. Errors have paths and suggestions like configs do.
- **Application**: a theme becomes `--fc-*` custom properties on the provider's (or the form's)
  own element. Nothing outside it is styled, and the built-in stylesheet only targets `.fc-*`
  classes. Switching theme or colour scheme restyles in place without remounting forms.
- **Host frameworks**: there is no runtime styling engine. Tailwind, CSS Modules or plain CSS hosts
  can read the tokens (`var(--fc-primary)`) or override any `.fc-*` class (selectors are single
  classes, so no `!important` is needed).

Custom components read the active theme with `useTheme()`:
`const { vars, theme, scheme } = useTheme(); style={{ color: vars.primary }}`.

## Custom components and actions

Register a spec (validated by the compiler) together with its React implementation:

```tsx
import {
  defaultRegistry,
  defaultActionRegistry,
  type FieldComponentProps,
} from '@form-config/react';

function Rating({ props, value, onChange, error, inputRef }: FieldComponentProps) {
  /* ... */
}

export const registry = defaultRegistry.extend([
  {
    spec: {
      type: 'rating',
      description: 'Choose 1 to max stars.',
      kind: 'field',
      props: {
        label: { type: { kind: 'string' }, required: true, description: 'Label.' },
        max: { type: { kind: 'integer', min: 2 }, default: 5, description: 'Stars.' },
      },
      value: { type: 'number', empty: null },
      events: ['change'],
      effects: ['show', 'hide', 'require', 'optional'],
      accessibility: 'Radiogroup of star buttons.',
      children: false,
      contexts: ['form', 'repeater'],
    },
    component: Rating,
  },
]);

export const actions = defaultActionRegistry.extend([
  {
    spec: {
      id: 'app.fill_example',
      description: 'Fill example answers.',
      events: ['click'],
      args: {},
      contexts: ['single', 'pages'],
      effects: 'Sets fields.',
    },
    run: ({ form }) => form.setValue('name', 'Example'),
  },
]);
```

Create registries once, at module scope. Re-registering an existing type throws unless you pass
`{ override: true }`; `withComponent(builtInDefinitions.text, MyInput)` replaces a built-in's look
while keeping its spec and behaviour. A field component never owns its value: it receives `value`,
`onChange`, `onBlur`, `inputRef`, `error` and its effective `required`, `disabled` and `options`.

## Generating configs with a model

The library calls no model. It gives an integration what it needs:

```ts
import {
  describeCatalog,
  configJsonSchema,
  compileConfig,
  groupIssues,
  applyRepairs,
  defaultCatalog,
} from '@form-config/core';

const catalog = defaultCatalog.pick(['text', 'select', 'date', 'checkbox']);
const prompt = JSON.stringify(describeCatalog({ catalog })); // compact, task-specific
const schema = configJsonSchema({ catalog }); // for structured output

const result = compileConfig(generated, { catalog, handlers: ['app.submit'] });
if (!result.ok) {
  for (const group of groupIssues(generated, result.errors)) {
    // Ask the model to regenerate just group.fragment (one component, page or dependency),
    // given group.issues, then:
  }
  const repaired = applyRepairs(generated, [{ path: '/components/3', value: fixedComponent }]);
}
```

The JSON Schema narrows what a model can emit; `compileConfig` still checks everything the schema
cannot express (references, placement, cycles), so always compile the result.

## Read-only answers

```tsx
<SchemaResponse config={config} values={submittedValues} />
```

Lays answers out like the form (labels, option labels, repeater rows), leaves hidden fields out,
and holds no form state.

## Known limitations

- **Styling** is functional, not yet designed: spacing, type scale and component details need a
  visual pass. Everything goes through tokens, so that pass will not change the API.
- **Components not built yet**: tabs, dialogs and drawers (and their actions `dialog.open` and
  `dialog.close`), tables, file upload and a date picker beyond the native one. Option lists come
  from the config or an `options` effect; registered option sources (looked up by name at runtime)
  are not implemented.
- **Repeaters do not nest.** A repeater inside a repeater's item is rejected.
- **Mount cost of very large forms**: about 0.15 to 0.3 s for 500 fields and 0.5 to 1.1 s for
  1,000 in Chrome on an Apple M1. Typing stays constant-cost at every size. Virtualisation is not
  implemented.
- **Bundle**: Base UI is most of the added weight (see the benchmarks); the AI helpers tree-shake
  away, but optional components are not split into lazy chunks yet.
- **Patterns** are regular expressions from the config. They are length-limited and compiled with
  the `u` flag, but a pathological pattern can still be slow; keep config authors trusted or
  review patterns.
- **Accessibility** has been checked with semantic markup, keyboard tests and focus checks, not
  with a screen reader or an automated axe run.
